
# Open-ChatBot Project Guidelines
Version: 1.1  
Status: Foundational Engineering Specification  
Scope: Entire Project Architecture, AI Systems, Frontend, Backend, Database, Prompting, State Systems, and Testing Infrastructure

---

# 0. Operational Environment Mandate
*   **Operating System**: Windows (win32).
*   **Shell**: PowerShell.
*   **Execution Rule**: Always use PowerShell-compatible syntax for shell commands (e.g., `New-Item` instead of `touch`, `Remove-Item` instead of `rm`).
*   **Pathing**: Use backslashes `\` or PowerShell-compatible forward slashes.

---

# 1. Project Vision

Open-ChatBot is designed to be a highly immersive, modular, scalable AI character interaction platform inspired by systems such as Character AI and Janitor AI, while maintaining full architectural flexibility and developer extensibility.

The platform must support:
- Persistent AI characters
- Distinct personalities
- Emotional continuity
- Dynamic prompt injection
- Stateful interactions
- Advanced frontend immersion
- Long-term scalability
- Modular AI systems
- Clean engineering practices
- Fully isolated testing infrastructure

The project should prioritize:
1. Immersion
2. Character consistency
3. Scalability
4. Modularity
5. Reliability
6. Maintainability
7. Frontend/backend synchronization
8. Testability
9. Extensibility

---

# 2. Core Response Architecture

The AI response pipeline follows the architecture below:

```text
Master Prompt
+ Character Prompt
+ Dynamic Character Tags
+ Character State Modifiers
+ Memory Context
+ User Context
= Final AI Response
````

Every response generated by the system must pass through this pipeline.

---

# 3. Prompt System Architecture

## 3.1 Master Prompt

The Master Prompt defines:

* Global AI behavior
* Formatting rules
* Safety constraints
* Writing style constraints
* Narrative consistency rules
* Output structure
* System-wide behavioral expectations

The Master Prompt acts as the foundational behavioral layer for every character.

---

## 3.2 Character Prompt

Each character must contain a dedicated character prompt that defines:

* Personality
* Tone
* Speech style
* Humor style
* Emotional tendencies
* Behavioral traits
* Relationship tendencies
* Social dynamics
* Character quirks
* Roleplay behavior

Character prompts should create highly differentiated personalities.

No two characters should feel identical.

---

## 3.3 Dynamic Tag System

Tags are modular behavioral modifiers attached to characters.

Examples:

* sarcastic
* obsessive
* dominant
* awkward
* affectionate
* chaotic
* tactical
* emotionally distant

Tags influence:

* Dialogue style
* Reaction patterns
* Emotional behavior
* Decision making
* Tone shifts
* Relationship dynamics

---

## 3.4 Automatic Tag Generation

The AI system should be capable of:

* Analyzing character descriptions
* Detecting implied personality traits
* Suggesting relevant tags
* Auto-generating behavioral metadata

This process should be deterministic and explainable where possible.

# 5. Narrative Response Formatting System

All AI responses must use a structured formatting system.

---

## 5.1 Formatting Rules

### Internal Thoughts

Use italic formatting:

```markdown
*I don't think this is a good idea...*
```

Represents:

* Thoughts
* Internal monologue
* Emotional reactions
* Subconscious processing

Frontend rendering should:

* Display italics
* Optionally dim/gray text
* Differentiate visually from dialogue

---

### Physical Actions

Use bold formatting:

```markdown
**She slowly closes the door.**
```

Represents:

* Movements
* Gestures
* Physical interactions
* Scene actions

---

### Dialogue

Use normal text:

```text
"I understand what you mean."
```

Represents:

* Spoken dialogue
* Normal narration
* Standard communication

---

## 5.2 Frontend Rendering Rules

The frontend renderer must:

* Correctly parse markdown formatting
* Preserve formatting consistency
* Support live rendering
* Maintain responsive display behavior
* Avoid formatting corruption

Formatting should remain consistent across:

* Mobile
* Desktop
* Tablets
* Different browsers

# 6. State Systems

The platform contains dynamic gameplay-like state systems.

---

## 6.1 Core Systems

### Energy

Represents:

* Fatigue
* Motivation
* Physical readiness

Behavioral effects:

* Slow responses
* Reduced enthusiasm
* Tired dialogue

---

### Hunger/Food

Represents:

* Hunger levels
* Physical discomfort

Behavioral effects:

* Irritation
* Food references
* Reduced patience

---

### Relationship/Affection

Represents:

* Trust
* Emotional closeness
* Bond progression

Behavioral effects:

* Increased warmth
* Emotional openness
* Trust dynamics

---

## 6.2 State-to-Behavior Mapping

Numerical values should never remain purely numerical.

The system must convert numerical states into:

* Descriptive prompt modifiers
* Emotional context
* Behavioral instructions

Example:

```text
Energy: 15%

Prompt Modifier:
"The character is extremely exhausted, mentally drained, and struggling to remain focused."
```

---

# 7. Frontend/Backend Synchronization Rules

Frontend and backend systems must evolve together.

Whenever backend systems change:

* Frontend UI must be updated
* API integrations must be updated
* State handling must be updated
* Rendering logic must be updated

The frontend must never become architecturally outdated relative to backend logic.

# 9. Global Testing Isolation Ruleset

THIS SECTION IS A NON-OPTIONAL FOUNDATIONAL ENGINEERING STANDARD.

Every test in the entire project must follow these rules without exception.

---

# 9.1 Zero Production Contact Policy

Under no circumstance may tests:

* Access production databases
* Modify real user data
* Read production state
* Share persistence layers with live environments

The production database (`chatbot.db`) must NEVER be touched by tests.

---

# 9.2 Mandatory Environment Isolation

All tests must execute inside isolated environments.

Supported isolation methods:

* In-memory SQLite
* Temporary isolated database files
* Disposable containers
* Ephemeral environments

Every test suite must:

* Provision its own environment
* Generate isolated state
* Self-clean after completion

---

# 9.3 Required Test Categories

The system must support:

* Unit tests
* Integration tests
* E2E tests
* Load tests
* Stress tests
* Regression tests
* Prompt validation tests
* Frontend rendering tests
* AI consistency tests
* State synchronization tests

---

# 9.4 Dynamic Test Generation

Tests should support:

* Dynamic data generation
* Dynamic character generation
* Mock prompt generation
* Procedural scenario creation

Avoid static brittle test structures where possible.

---

# 9.5 Cleanup Enforcement

All tests must automatically remove:

* Temporary databases
* Files
* Mock assets
* Cache entries
* Generated state

No test artifacts should persist after completion unless explicitly configured for debugging.

---

# 9.6 Parallel Execution Safety

Tests must support:

* Concurrent execution
* Isolated resource allocation
* Independent state management

Tests must never:

* Share mutable state
* Lock global resources unnecessarily
* Depend on execution order

---

# 9.7 Deterministic Testing Requirements

Tests must be reproducible.

Where randomness exists:

* Use seeded randomness
* Log seeds when failures occur
* Ensure replay capability

AI-related tests should support:

* Mock AI responses
* Snapshot validation
* Behavioral consistency checks

---

# 9.8 Frontend Testing Requirements

Frontend tests must validate:

* Markdown rendering
* Real-time UI updates
* Responsive behavior
* API synchronization
* Error handling
* State rendering consistency

---

# 9.9 Backend Testing Requirements

Backend tests must validate:

* Prompt assembly
* Character consistency
* CRUD systems
* Database integrity
* State synchronization
* API correctness
* Memory persistence

---

# 9.10 Failure Recovery Testing

The system must test:

* Partial failures
* Database corruption scenarios
* Interrupted requests
* Invalid prompt states
* Malformed data
* Concurrent update conflicts

---
