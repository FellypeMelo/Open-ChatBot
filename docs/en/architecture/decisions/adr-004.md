# ADR 004: Programming Language & Orchestration Architecture

## Status
Accepted

## Context
The user requested an evaluation of the best language for the system, prioritizing "Maximum Performance Mode." The core heavy lifting (LLM inference) is handled by `llama.cpp` (C++). The "Orchestration Layer" manages prompts, lorebooks, and the frontend bridge.

## Decision
We will continue using **Python (FastAPI)** for the orchestration layer, but with strict **High-Performance Directives**:

1.  **Async-First**: All I/O operations (llama.cpp communication, database, logging) must be asynchronous.
2.  **Native Performance Extensions**: 
    *   **JSON**: Use `orjson` (Rust-based) for ultra-fast serialization.
    *   **Vector Ops**: Use `faiss-cpu` or `annoy` (C++ bindings) for lorebook retrieval.
3.  **Process Isolation**: The `llama.cpp` binary will run as a separate managed process, ensuring its performance is not throttled by the Python runtime.

## Rationale
*   **Agility**: The complex prompt-stitching and state-to-behavior logic (Scripts/Lorebooks) is significantly faster to develop and iterate in Python.
*   **Bottleneck Analysis**: In a single-user local environment, the overhead of Python's orchestration (a few milliseconds) is negligible compared to the inference time of the model itself (hundreds of milliseconds).
*   **Extensibility**: Python has the most mature ecosystem for AI-related middleware (LangChain, ChromaDB, etc.).

## Alternatives Considered
*   **Rust (Axum/Actix)**: Maximum raw performance, but would significantly slow down the implementation of the flexible "Behavioral Scripts" and "Lorebook" logic.
*   **Go**: High concurrency, but lacks the rich AI/Math library ecosystem required for future-proofing (RAG/Summarization).
