# ADR 004: Linguagem de Programação e Arquitetura de Orquestração

## Status
Aceito

## Contexto
Foi solicitada uma avaliação da melhor linguagem para o sistema, priorizando o "Modo de Máxima Performance". O trabalho pesado central (inferência de LLM) é feito pelo `llama.cpp` (C++). A "Camada de Orquestração" gerencia prompts, lorebooks e a ponte com o frontend.

## Decisão
Vamos continuar usando **Python (FastAPI)** para a camada de orquestração, mas com **Diretrizes estritas de Alta Performance**:

1.  **Async-First**: Todas as operações de I/O (comunicação com o llama.cpp, banco de dados, logging) devem ser assíncronas.
2.  **Extensões de Performance Nativa**:
    *   **JSON**: Usar `orjson` (baseado em Rust) para serialização ultrarrápida.
    *   **Operações Vetoriais**: Usar `faiss-cpu` ou `annoy` (bindings C++) para a recuperação do lorebook.
3.  **Isolamento de Processo**: O binário do `llama.cpp` vai rodar como um processo gerenciado separado, garantindo que sua performance não seja limitada pelo runtime do Python.

## Justificativa
*   **Agilidade**: A costura complexa de prompts e a lógica de estado-para-comportamento (Scripts/Lorebooks) são significativamente mais rápidas de desenvolver e iterar em Python.
*   **Análise de Gargalo**: Em um ambiente local single-user, o overhead da orquestração em Python (alguns milissegundos) é negligenciável comparado ao tempo de inferência do próprio modelo (centenas de milissegundos).
*   **Extensibilidade**: Python tem o ecossistema mais maduro para middleware relacionado a IA (LangChain, ChromaDB, etc.).

## Alternativas Consideradas
*   **Rust (Axum/Actix)**: Performance bruta máxima, mas atrasaria significativamente a implementação dos "Scripts Comportamentais" e da lógica de "Lorebook" flexíveis.
*   **Go**: Alta concorrência, mas carece do ecossistema rico de bibliotecas de IA/Matemática necessário para se preparar para o futuro (RAG/Sumarização).
